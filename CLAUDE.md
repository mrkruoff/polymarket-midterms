# polymarket-midterms

Tracks Polymarket and Kalshi prices on the 2026 midterm races (Senate, House,
governor) and scores them after Nov 3, 2026. README.md has the workflow,
scoring rules, and venue caveats; `pm_common.py` and `kalshi_common.py` are the
shared modules.

## Git workflow

**Data-only updates may be committed, merged, and pushed directly on `main`.**
This covers the daily job (`run_daily.py`) and the same outputs regenerated by
hand: the files that running the existing scripts produces, with no code
changes. That means:
- `data/snapshots/`, `data/universe.json`, `data/history.csv`
- `data/candidates.csv` (including hand-filled parties, `party_source=manual`)
- `data/resolutions.csv`, `data/results.json`
- `docs/data.json`

**Anything that changes logic or features goes through a PR.** Work on a
feature branch, then open a PR for review (create-pr skill). Never merge it or
push it to `main` yourself, not even as a local fast-forward. This covers:
- any `.py` file
- `docs/index.html`, `README.md`, `.gitignore`, this file
- curated inputs that change what gets collected (`data/kalshi_scraped.txt`,
  `data/kalshi_events.json`)

If a change mixes both, or it's unclear which side it's on, treat it as a PR
change and ask. A question like "can we look at merging?" is a question, not a
go-ahead.

## Notes

- The launchd job commits to whatever branch is checked out and pushes `main`.
  Leave the working tree on `main` when you're done on a branch.
- While a feature PR is open, the daily commits on `main` touch the same data
  files. Resolve conflicts by merging `main` into the branch and regenerating
  the data, not by hand-editing CSV/JSON.
- `data/raw/` is gitignored; never commit it.
